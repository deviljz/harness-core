# 修 Bug 质量闭环（预算闸门 + 红绿复现 + 独立审 Diff）

修 bug 最容易出事故的不是写错语法，而是**方向改偏、为边缘情况加新机制、或者把核心枢纽文件叠成补丁山**。动手前先过预算闸，改完先过独立复核再交卷。

## 第 0 步：动手前过「改动预算硬闸门」（最关键）

- **绿灯直接干**：预计改动 **≤3 个运行代码文件**、**净增 ≤80 行**、**不新增状态标记 / 缓存文件 / 重试或锁定机制**、不改核心枢纽文件的公共状态流转、不改用户可见交互 → 直接进第 1 步。
- **红灯强制刹车（严禁直接写代码）**：只要触碰以下任意一条，动手前必须先给用户 **5 行方向卡** 拍板：
  1. 预计动超过 3 个运行代码文件，或净增 >80 行运行代码；
  2. 需要新增**任何新状态变量、新缓存、新门控、新重试或锁定机制**；
  3. 需要改动项目 `.harness/config.yaml` 中登记的**核心枢纽文件**（`diff_budget.hub_files`）的公共状态机，或改变用户可见交互/视觉样式；
  4. 所修问题属于边缘/极端场景。
- **红灯方向卡必须先答 3 个问题（减法优先）**：
  1. **能不能做减法？**——能不能通过“删掉/退回之前过度防御的旧补丁”解决，而不是再叠一层 `if`？
  2. **能不能不加新机制？**——如果属极低概率边缘情况，能不能直接“记日志上报”或沿用旧版最简单行为？
  3. **影响面**：拟改哪几个文件、旧版 / 无 Lua / 同类正常页面怎么做的？

## 第 1 步：先红后绿（防盲改）

- 修改前必须先用最小测试、录屏或截图**把问题复现成失败（红）**（如已有明确修前日志/截图且当前代码实锤复现亦可）。
- 改完用**同一套条件/用例**重跑成通过（绿）。拿不出修前红 vs 修后绿对照的，不许报“已修好”。
- 全程遵守 `existing-flow-review`（优先复用现有组件与函数；动 UI 先对照 1～2 个同类正常页面）。

## 第 2 步：硬工具自检 + 独立子 Agent 审 Diff

1. **跑确定性硬检查**：
   ```powershell
   python -m harness diff-guard
   python -m harness check --warn-only
   ```
   - 若 `diff-guard` 亮红灯（未提前获用户批准却悄悄超预算或动了核心枢纽文件），**必须缩减/拆分改动或向用户亮红灯说明**，严禁带着未授权大改直接交差。
2. **独立干净子 Agent 审 Diff（替用户当反方）**：
   - 写完代码后，由总控派一个**没参与写代码的干净子 Agent**只看 `git diff` + 原流程入口，专门拷问 4 件事：
     1. 有没有过度防御、新增多余状态/锁，或另起炉灶重复造轮子？
     2. 有没有破坏原流程、无 Lua 模式或旧存档兼容？
     3. 动 UI 有没有对齐项目里同类正常页面？
     4. 测试是不是只测了“新路径能跑”，漏了失败重试、重启恢复或缓存层（如 Redis/MySQL）一致？
   - 发现硬伤**直接打回修复子 Agent 重改**，不拿半成品烦用户。

## 第 3 步：3 行交卷卡 + 一单一小提交

- 过了硬检查和独立 Review 后，只交 3 样硬证据：
  1. **改动清单**：改了哪几个文件 + `diff-guard` 行数统计；
  2. **红绿对照**：修前失败证据 vs 修后通过证据；
  3. **独立 Review 结论**：无硬伤（或仅剩 1 个需用户拍板的取舍）。
- **严禁巨无霸提交**：每个 bug 独立一笔干净小提交，不把多个 bug 和大重构揉在一起，方便随时单条回退。

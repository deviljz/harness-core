# Bug 调查与查因轻护栏

排查问题不是写重型 Spec，也不是边猜边改代码。默认**一条条处理**，按以下 4 条护栏推进，让用户每查完一条都能在 3 秒内决定“直接过 / 自己修 / 派子 Agent 修并继续下一条”。

## 1. 默认只读，不提前改业务代码

- 排查阶段只读源码、配置、日志和已有报告；允许跑只读检索或已有复现脚本，**不擅自修改业务代码、资源文件或回退用户未提交改动**。
- 确需加临时日志或单点复现探针才能拿证据时，优先走已有测试/诊断入口；若必须改动业务代码，先说明要验证的假设和还原方式。
- 用户明确要求顺手修或确认改点后，再进入修改，并复用原流程（配合 `existing-flow-review`）。

## 2. 第一行先给 3 秒定性，正文把事实 / 推断 / 未验证分层

面向用户的回复，**第一行必须先给明确决断定性**（三选一），再列简短证据：

- `定性：无需改代码`（已有修复/非缺陷/直接交复测或等补充现场日志）
- `定性：确认需改代码`（已定位根因与改点，可直接改或派子 Agent 改）
- `定性：待补一步最小验证`（写出缺哪一个关键证据即可拍板）

正文证据必须分层，不把猜测写成结论：

- **已核实事实**：精确到 `文件:行号`、日志原文、复现条件与实际观察结果。
- **基于事实的推断**：说明哪条证据推导出该假设，以及还有哪些备选解释。
- **未验证项**：明确写出“在条件 X 下观察到 Y；尚未测试 Z，因此暂不能判断 W；下一步最小验证是 T”。

## 3. 最小有界验证；确认要改时顺手产出“子 Agent 可直接接手的修复包”

- 从**真实入口**顺着调用链往下查（入口 → 请求/消息/状态变更 → 持久化/回包 → 异常兜底与重启恢复），不漫无目的地全仓盲扫。
- 连续两轮没有新增证据时停下来重审前提假设，不在同一条死胡同里打转。
- 一旦定性为 **`确认需改代码`**，顺手附上 4 行精简修复任务包（无论直接改还是交给子 Agent 改、主线程继续查下一条，都能直接开干且不撞车）：
  1. **根因与改点**：精确 `文件:行号` + 原流程入口
  2. **最小改法**：优先复用现有函数/链路，不另造平行规则
  3. **改动边界**：只动哪些文件（避免与并行排查/修复的其他 bug 冲突）
  4. **验收标准**：跑哪条既有脚本或看哪条日志/现象算通过

## 4. 查完默认落盘到换班卡，不随便改 git 里的历史报告

- **默认落盘位置**：更新当前项目的 `.harness/handoff.md`（通过 `python -m harness handoff` 定位，已被 `.gitignore` 忽略，不污染项目 git）。
- **只有用户明确要求**写入某份正式文档时，才修改 `doc/` 下的已有报告，避免把共享历史表格改乱。
- 每条记录保持精炼（4 栏：已验证事实 / 已排除原因 / 未决项 / 下一步最小动作或派发状态）。
- 面向用户说人话，不把原始长日志或整段源码倾倒进聊天；查完当前条后等用户决定“改 / 派子 Agent / 继续下一条”，不擅自跳过或连改多条。

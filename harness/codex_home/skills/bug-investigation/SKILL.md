# Bug 调查与查因轻护栏

排查问题不是写重型 Spec，也不是查一半跑回来问用户“要不要再看一眼”。默认**一条条查透**，能本机自主验证的**全部先自己验完**，带着可决断结论再叫用户拍板（直接过 / 自己修 / 派子 Agent 修并继续下一条）。

## 1. 默认只读，不提前改业务代码；本机能验的自己直接验完

- 排查阶段只读源码、配置、日志和已有报告；允许自主运行只读检索、日志分析或项目已有复现/验证脚本，**不擅自修改业务代码、资源文件或回退用户未提交改动**。
- **不要把“自己本来能查、能跑的最小验证”留给用户或停下来请示**——只要在现有只读/测试脚本权限内、不改业务代码且无额外授权/费用风险，直接自己验完，拿到结果再汇报。
- 只有确实**必须改业务代码/打新包插桩**，或需要用户新增授权、真机人工操作、向 QA 要现场日志时，才停下来请示或说明缺口。

## 2. 第一行先给 3 秒决断定性，正文把事实 / 推断 / 未验证分层

面向用户的回复，**第一行必须先给明确决断定性**，再列简短证据：

- `定性：无需改代码`（已有修复 / 非缺陷 / 现有条件已通过）
- `定性：确认需改代码`（已核实根因与改点，等你拍板直接改或派子 Agent 改）
- `定性：卡在外部条件`（**仅限本机确实做不了的情况**：如缺 QA 原现场日志、必须真机人工复现、或必须改业务代码插桩；写清缺哪一项外部条件）

正文证据必须分层，不把猜测写成结论：

- **已核实事实**：精确到 `文件:行号`、日志原文、复现条件与实际观察结果。
- **基于事实的推断**：说明哪条证据推导出该假设，以及还有哪些备选解释。
- **未验证项**：明确写出“在条件 X 下观察到 Y；因缺外部条件 Z 尚未测到，暂不能判断 W”。

## 3. 沿真实入口查透；确认要改时顺手产出“子 Agent 可直接接手的修复包”

- 从**真实入口**顺着调用链往下查（入口 → 请求/消息/状态变更 → 持久化/回包 → 异常兜底与重启恢复），不漫无目的地全仓盲扫。
- 连续两轮没有新增证据时停下来重审前提假设，不在同一条死胡同里打转。
- 一旦定性为 **`确认需改代码`**，顺手附上 4 行精简修复任务包（无论直接改还是交给子 Agent 改、主线程继续查下一条，都能直接开干且不撞车）：
  1. **根因与改点**：精确 `文件:行号` + 原流程入口
  2. **最小改法**：优先复用现有函数/链路，不另造平行规则
  3. **改动边界**：只动哪些文件（避免与并行排查/修复的其他 bug 冲突）
  4. **验收标准**：跑哪条既有脚本或看哪条日志/现象算通过

## 4. 查完默认落盘到任务板/换班卡，不随便改 git 里的历史报告

- **多条任务并进时**：优先用 `python -m harness task update <id> ...` 落盘到 `.harness/tasks.json`（自动校验 `need_fix` 必填字段并生成 1 页 `.harness/tasks.md`）；如一次汇报多条，必须给紧凑总表（编号 / 定性 / 结论），**凡标 `确认需改代码` 的必须附 4 行修复包，禁止混在散文里一带而过**。
- **单条换班落盘**：更新 `.harness/handoff.md` 时**覆盖精简、严格保持 ≤60 行**（已查完条目压缩成 1 行索引，禁止每次往末尾无限追加成流水账）。
- **只有用户明确要求**写入某份正式文档时，才修改 `doc/` 下的已有报告，避免把共享历史表格改乱。
- 面向用户说人话，不把原始长日志或整段源码倾倒进聊天；查完当前条后等用户决定“改 / 派子 Agent / 继续下一条”，不擅自改业务代码，也不擅自跳过。

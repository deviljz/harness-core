# Bug 调查与查因轻护栏

排查问题不是写重型 Spec，也不是边猜边改代码。按以下 4 条护栏推进，保证结论可决断、过程不污染工作区。

## 1. 默认只读，不提前改业务代码

- 排查阶段只读源码、配置、日志和已有报告；允许跑只读检索或已有复现脚本，**不擅自修改业务代码、资源文件或回退用户未提交改动**。
- 确需加临时日志或单点复现探针才能拿证据时，优先走已有测试/诊断入口；若必须改动业务代码，先说明要验证的假设和还原方式。
- 用户明确说“查完顺手修”时，也要先把根因核实清楚再动手改，并复用原流程（配合 `existing-flow-review`）。

## 2. 事实 / 推断 / 未验证必须分层

汇报和记录时明确拆开，不把猜测写成结论：

- **已核实事实**：精确到 `文件:行号`、日志原文、复现条件与实际观察结果。
- **基于事实的推断**：说明哪条证据推导出该假设，以及还有哪些备选解释。
- **未验证项**：明确写出“在条件 X 下观察到 Y；尚未测试 Z，因此暂不能判断 W；下一步最小验证是 T”。

## 3. 最小有界验证，给出可决断结论

- 从**真实入口**顺着调用链往下查（入口 → 请求/消息/状态变更 → 持久化/回包 → 异常兜底与重启恢复），不漫无目的地全仓盲扫。
- 优先找能一刀切开两个假设的**最小对照测试**（如看一条具体日志、查一处原入口、跑单条用例），拿到可决断结果就收手，不为了凑字数扩展无关检查。
- 连续两轮没有新增证据时停下来重审前提假设，不要在同一条死胡同里打转。

## 4. 查完落盘一小段活结论

- 优先更新项目已有 QA 报告、整改清单或本轮 4 栏换班卡片（`python -m harness handoff`），**不要另建一堆平行日志目录**。
- 落盘内容只留 4 块（控制在一页以内）：
  1. **已验证事实**（含 `文件:行号` / 日志证据）
  2. **试过确认不行的路 / 已排除原因**（避免后续重复踩坑）
  3. **未决项**（仍需真机/日志/决策确认的点）
  4. **下一步最小动作**（具体到改哪一处或跑哪条验证命令）
- 面向用户汇报先说**结论 + 实际影响 + 下一步建议**，说人话，不把原始长日志原样倾倒进聊天。

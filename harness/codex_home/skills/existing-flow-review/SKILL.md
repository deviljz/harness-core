# 原流程核对与回归

用实际代码和运行证据判断需要补什么，避免漏掉已有的兜底路径，或把原有流程换成另一套业务规则。遵循当前生效的 AGENTS.md 和用户授权，不把其中规则再复制成另一份长期规范。

## 从真实入口核查

- 定位相关入口、现有测试、调用方及返回位置。优先用 rg 精确查找并按调用关系继续，不全仓遍历源码或反复运行 Git 扫描。
- 跟踪与改动有关的正常处理、异常或数据不足时的兜底。涉及状态时，核对数据来源、更新时机、缓存失效、存档与重启恢复；涉及网络时，检查相关的相邻消息、增量同步、确认和重传。
- 找到已有的补充实现和共同入口。例如离线逻辑需要机器人资料时，同时检查原来的补机器人和按 ID 查资料路径，而不只看当前匹配回包。
- 涉及 UI 布局、遮罩、提示条或弹窗改动时，动手前先对照项目里至少 1～2 个同类正常页面的现有做法，优先复用统一的公共组件与视觉套路，避免凭空手拼局部色块或违和样式导致反复返工。
- 保留决定方案所需的少量文件位置、函数名或验证结果，区分事实、推断和未验证项。一条消息没有字段或一次搜索未命中，不足以判定系统缺少该能力。

## 选最小适配

优先调用现有函数、调整条件或数据来源，必要时少量提取公共函数。核对复用是否保留业务语义与副作用，不能只沿用名称、重写其余规则。

确需相似实现或较大重构时，简短说明原来怎么做、新需求改变了什么、哪个环节无法满足，以及为何更小适配不够。普通修复按已有授权继续；确有新增授权缺口或长期双份维护取舍时才请用户决定。

用户只要求调查或讨论时，给出证据与建议，保持业务代码不动。已获实现授权时，核查后继续完成改动，不停在流程分析。

## 按影响验证

- 对比改动前后同一行为的输入、结果、状态变化和副作用，不只检查新入口返回成功。
- 按风险回归有关边界：在线/离线、已有/缺失缓存、首次/重启恢复、数据不足、失败重试。只做必要测试，不为文字修改或实现细节堆测试。
- 检查新增的重复规则、重复状态、重复执行，以及无必要的网络数据、持久化数据和玩家限制。
- 收敛本轮新增的临时重复实现，不删除无关旧功能或扩大无关重构。

最终简明报告原流程证据、实际改动、验证结果及未验证项。不粘贴聊天正文、源码或密钥；用函数与文件位置说明依据。

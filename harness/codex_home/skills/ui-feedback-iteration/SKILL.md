# UI 使用反馈与流程迭代

每轮在维护者工作区留一份可接续的复盘。开始或恢复时先读本轮原目标、上次问题表和用户已作的取舍。用户陆续发反馈时先索引来源和现象，等对方说发完再排整轮优先级。用户暂时追问某个问题，只更新它在表里的状态。用户明确改变目标时再调整范围。

用户说“继续”时，先看上一句有没有指定仍须完成的动作；有就接着做。该动作已完成时，取周报“建议的迭代顺序”中第一个现在能执行的未完成项。标为“等下次真实任务观察”的项保留待观察。若要改变已定顺序，说明哪条新证据改变了优先级。

## 从记录到问题

1. 先列收到哪些包、各自覆盖什么项目、角色、版本和时间。相同事件跨包出现只算一次。把旧版本、之后新增的需求以及此次没有样本的角色标出来。
2. 对照之前的诊断逐条核查。读用户当时的要求和反馈，再查对应的原图、实际输出、操作记录或版本。优先查影响最大的差异，以及可能推翻原判断的反例。索引与原记录冲突时列出冲突和依据。一份报告写了通过，只能证明它实际检查过的内容。
3. 按可以独立修复或验证的原因归类，保留稳定编号。每项记下 **用户看到什么｜案例证据｜最早在哪步出问题及把握｜优先级｜当前状态与下一步**。原因拿不准就给待验证的假设。区分规则缺口、已有规则未执行、工具漏检、输入版本或需求变化。只有程序使用记录时，结论限于程序实际经过的环节。
4. 优先处理会做错操作、明显改变整页观感、跨页重复返工或错误放行的问题。将用户已接受的细微差异、已改变的需求和缺少证据的线索留在表中，说明暂缓理由。交付时让人能看到哪些仍未处理。

## 从问题到一次改动

- 先选一个最能区分好坏的真实案例，写下旧结果、预期结果、通过条件和一个应该保留的正确例子。多个问题可以共用一套输入，但各自判定。做独立制作、流程执行、事后看图三种测试时，结论只覆盖实际测试的环节。
- 旧流程能否暴露问题，尽量用保存的失败截图、产物、对话和最小重放判断。复现不了就交代边界，换更接近原问题的案例或保留待观察。规则已存在时查正常入口有没有调用、有没有证据，优先修实际断点；避免用重复说明掩盖执行遗漏。
- 用户只要求分析时，止于结论和建议。获准实施后，按同样判据比较改前、改后，并检查一个好例是否退步。大批重跑、开新工程和人工审批都需要具体理由。已有素材足以裁决就停。
- 默认先拿已有的一对好坏样本做最短验证。它已能判断本次改动，就在这里收尾。仅有文字规则变化时，通常一次对照已足够。再开工程、加测试或增加复核人，要能说明会改变哪个判断。引用他人指认的重大差异时，直接打开对应原件核对。
- 更新同一份问题表。区分“历史反馈”“已复现”“已改待验证”“样本验证通过”“暂缓”。列出本次推进的编号和其余高优先项。更正旧判断时留下日期、反证及影响。有一个样本通过只关闭对应的验证项，整轮结论仍按全部反馈更新。

简报只回答三件事：这轮影响最大的是什么，现有证据能说明到哪里，下一笔时间花在哪。链接到原证据和完整问题表即可。

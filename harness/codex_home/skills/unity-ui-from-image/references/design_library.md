# 通用设计规范的整理与维护

用于用户提供的美术规范、组件示意、状态图或视频。先明确本轮是整理草稿、确认设计、匹配实现还是制作组件；整理规范不等于获准改Prefab。

## 三种输出，只有一份维护源

- 原图/视频：原样保存并记录来源与哈希，说明原设计版本是否已知。导入日期不是设计版本。
- 每条规范的YAML：记录用途、组合层级、参数、可变字段、状态、引用规范、未知项与设计版本；为AI检索和维护提供结构。
- 自动生成的HTML：展示来源、规范说明、差异和实现状态。不能独立手改HTML里的规则形成第二份标准；设计参考图与真实Unity渲染明确区分。

按真实职责划分样式/处理方式、组合组件、页面/业务示例；不强制一张图一个Prefab。图示中的名称、道具数量、价格通常是示例，不直接固化为业务规则。资源范围、百分比缩放、最小字号与自适应策略分别记录；设计像素不能脱离基准尺寸直接解释为最终屏幕像素。

OCR用于定位文字，结果须对照原图；未核对的参数不得自动进入组装。保留无法辨认的原文与未知值，不能为补齐字段猜资源名、颜色、尺寸或True Shadow参数。图、视频或项目实现有冲突时记录范围，先查已有资料，不默选最新文件时间作为最终设计。

## 先设计，后关联实现

准备资料→美术设计/使用规范→设计检查与交接→程序匹配或制作组件→页面组装。设计可先确认而Prefab尚未实现；已有项目允许从现存实现提取候选规范，但实现事实不自动代表美术批准。

设计确认状态、转录核对状态、Unity实现与验证状态分别记录。匹配实现时优先现有Prefab与数据入口；图片名相同不代表组合完整。未匹配时Prefab字段保持空，不能根据文件名编造已实现关系。

## 变更

修实现错误、全局规范升级、限定场景变体分开。改规范时记录原因、影响与版本；改Prefab时标记偏离/待核对，不自动推广为设计规范。关联索引支持找到受影响页面；自动变化检测只表示发现变化，不表示确认或回归完成。

初期用目录、YAML和HTML即可。先按本次任务整理，按需匹配组件，不为每条规范扫描全项目或搭建大型管理系统。确认后再用代表组件验证描述能否支持实施，不能仅凭HTML生成成功宣称可自动拼UI。

工具工作区 `scripts/build_design_library.py --library <目录>` 从YAML生成HTML、JSON索引与校验报告；核对来源哈希、标识和规范引用。它不自动批准设计、不解析Unity工程、不把OCR认作已核对内容。目录本身是可携带的项目资料，项目具体数值不写入本通用skill。


## 比较规范是否有帮助

做有/无规范对照时，两组保持同模型、素材/字体、工具与验收条件；用干净上下文，排除页面标注、旧页面Prefab/布局/生成器及结果记录的间接泄漏。规范组只增加约定的规范资料。保存输入哈希与实际调用记录，制作自述不能代替审计；资料包隔离不能冒称操作系统权限隔离。历史版本若输入更多或状态不同，只作参照，不并入严格因果结论。

报告实际采用的规范及其作用，分开素材选择、页面推断、执行错误和工具错误。没有明显改善也是有效结果；不能把单次比较写成普遍收益。确认可重复的组件后再关联实现，不因一张图仍有差异就把页面坐标和特殊修补扩成通用规范。

## 让程序执行规范，而不是让每个页面重新解释

这节属于程序实现阶段。美术规范先独立存在：美术使用图文目录中的稳定组件/样式编号、示例和可调字段，不要求持有Prefab或打开Unity；程序将同一规范版本关联到具体实现，再导出已验证能力给美术使用。规范新增/修订先变更设计版本，已有实现标记待适配；程序改Prefab不能静默覆盖设计要求。人工修改与依赖同步仍按既有增量核对流程执行。

**程序跨页选组件时，先定复用哪一层。** 找项目已确认的规范或一个已验收用法，看这个元素属于宿主还是本页、执行什么操作、哪些内容由数据填入。

- 宿主已经显示的公共栏由宿主保留；弹窗需要自己的余额入口时，可共用币面和金额组件，外框和位置按弹窗设计。
- 同用途、同结构的按钮沿用原组件和状态入口。颜色相近但触发操作、轮廓或图文结构不同，查项目是否已有对应变体。项目确认统一的部分按约定复用；档位插画、语言或业务配置允许变化的部分保留差异。
- 在现有选型记录里写一句“沿用什么、此处换什么、依据在哪”。具体调用哪个接口，要核对它接受的数据和触发的动作。只能确认外观相同时，先复用外观，业务入口留待查证。找不到项目约定时，标为本页选择；没有必要为这个判断先盘点全库或新建公共 Prefab。

已确认的共用设计优先落实为可执行组件。AI负责识别适用规范、匹配已有资源、补缺项和审美判断；程序负责生成或实例化、填数据、检查参数。不要让页面制作代理反复编写同一类组件。

1. **规范与实现分开关联。** 规范保存设计要求；实现记录规范版本、Prefab或生成器、资源映射、允许输入、入口是Editor生成还是运行时更新，以及实际验证过的数据/状态范围。静态Prefab存在或编辑器Fill成功，不等于已经有运行时更新能力。优先绑定已有组件与业务入口；缺少合适组件时才写通用生成器。确实只有Editor入口且本次需要动态内容时，最小适配只接收已格式化数据和显式状态，保持共用样式，不复制奖励/业务判断。生成器放Editor，不能为生成便利给正式UI挂多余运行脚本。
2. **先补齐能决定结果的缺项。** 基准尺寸、图标主体适配、层级、文字框锚点/位置、字体材质、字号/溢出方式、阴影和允许缩放必须有依据。可继承经过核对的Prefab结构，不必把每个Transform抄进YAML。项目原实现可以作为候选，不能自动当作设计批准。缺项输出清单或带标识的试作；不暗加默认值后声称合规。
3. **限制页面能改什么。** 通常仅传图标、数量、文案、已定义状态、位置和允许的组件尺寸；组件内部字号、文字偏移、层级、描边、阴影不由页面任意覆盖。整体等比缩放、局部伸缩或字号自适应须由该规范明确选择，不能统一替所有组件决定。合法例外登记为有适用范围的变体，不偷偷改实例。
4. **检查保存后的实际产物。** 反读Prefab和实例覆盖，核对规范ID/版本、字体材质及资源、结构/布局、缩放与样式。只核对“使用了规范”或生成器输入不足以通过。首次做代表验证时故意改变关键参数，确认检查确实会失败；对允许的动态内容不报误差。结构/字段一致与视觉合适分别验收，SSIM不能代替规则检查。
5. **只验证一次可复用部分。** 组件通过代表内容、长短文案和状态切换后锁定版本；后续页面复用，主要检查选型、位置、尺寸和新组合。设计或手工Prefab变化后标记受影响关联；查清是设计变更还是实现偏离，再更新规范/组件并回归，不静默反向改写规范。未改动组件不反复读图分析，减少token消耗。

### 先选组件，再确认页面尺寸，再验证代表格

1. **选型先看完整组件。** 同版本、同用途、结构/外观与目标效果图相符的原组件优先作为候选，连同图标、文字、状态层和填充入口核对。原实现不自动等于设计批准，项目里的通用Item也不自动适用于所有页面。原组件与通用规范冲突时，记录冲突及采用依据；少量有明确用途的差异可定义变体，结构/语义不符才另选组件，不悄悄混搭。
2. **页面使用尺寸单独登记。** 区分组件基准尺寸、图标框尺寸、可见主体范围、容器/底框尺寸、实例缩放和父级/Canvas缩放。追原页面Prefab覆盖、生成回调、布局组件及运行时设置；缺依据时从效果图测量并标为本页面暂定。某个页面的尺寸或比例、某次试作的旧值，都不能升级为项目统一参数。

项目为图标确认了离散尺寸档位时，从该项目的机器可读列表选择合适档位，并按图标实际显示框、实例缩放和父级Canvas适配换算；不要把图标档位直接赋给格框、底板或组件根。分别记录参考画布下的设计像素与换算后的设备像素。图标矩形框与透明留白内的可见主体范围不是一回事；保留源图边界，不自动trim或裁边。单次比例推导出的尺寸不等于已确认档位。项目档位只在所属项目内适用，不能复制成其他项目的通用数值。
3. **比较时固定条件。** 同一普通格/特殊格使用相同道具、数量、状态、目标容器、背景和渲染条件；两种组件各保留自身内部布局/字体/状态结构，使用有依据的整体尺寸策略。直接复用、剥离业务依赖后的视觉复用、重建近似要分别标明。业务依赖缺失时先查可复用显示子树或适配入口；剥离只能移除非视觉逻辑，必须列差异，不能把视觉提取写成原业务组件已完整接入。
4. **四项一起验收。** 容器本身的位置、组件占容器的比例、组件几何中心、内部图标/数字/状态关系都要检查。相同图片框可能因透明留白而有不同主体大小；字段与哈希检查不能替代实际尺寸对照。必要的换数据/状态检查与外观分别记录；静态正确不代表运行时显示链路正确。
5. **通过后固定使用记录。** 至少保留组件ID/版本、容器类型、尺寸/缩放策略、定位策略、依据与允许例外；整页实例只填允许的数据，不重新猜内部参数或显示尺寸。只做代表样时不修改整页；达到可用水平后停止精修，未确认的候选不自动推广成项目规范。

组件状态还须检查叠加结果：替换底图不代表最终可见的内底已改变，特殊边框自身的不透明内芯可能把新底图遮住。优先复用完整对应状态；确需补组合变体时，明确共用的内填充区域和层级，检查边缘/角饰不被覆盖，按显式数据切换并恢复，不能把截图中的某几个实例永久染色。沿用原实现也须对照效果图，原代码可能同样缺少目标组合。

### 尺寸判断：先核对尺度，再分项比较

适用于从效果图选择显示尺寸、调整尺寸档位或替换组件。目标是更接近已确定的设计，不是让画面更疏松。制作与复核都执行以下检查；缺少尺度依据时不能直接推荐换档。

1. **先统一尺度。** 确认效果图画布、实际渲染画布及换算比例；从保存后的实例读取图标框、祖先缩放和Canvas适配，得出参考画布下的图标显示尺寸。分别列出组件根和底框尺寸。不要把贴图文件尺寸、透明留白内主体大小、图标框或设备像素混为一谈。
2. **结论前必须生成同倍率局部对照。** 原图、当前版本和必要候选放在同一张局部图里，保留底框/相邻元素作为位置参照；不得各自裁紧再缩放到相同大小。标明候选尺寸，先看实际显示大小，再用所有列相同倍率放大。先检查截图颜色和裁切是否可靠，避免捕获错误干扰判断。位置影响观察时可另附仅平移对齐的诊断图，标明平移量并保留原位对照，不能缩放对齐来验证尺寸。
3. **分开给结论。** 每个候选分别记录：图标主体宽高与轮廓、数量文字大小/相对位置、底框大小、组件位置。至少指出可核对的轮廓端点或宽高关系；能可靠测量时记录参考与候选范围，遮挡/软边不清时用估计范围或未知，不编造精确像素。整体缩放同时改变图标、文字和底框时，写明哪些变好、哪些变差；数字不挤、底框更小或位置碰巧更近，都不能代替图标尺寸证据。
4. **复核看证据，不看推荐。** 给复核者同倍率对照和分项要求，不先给制作者偏好的档位。机器尺寸通过、多个模型意见一致都不能替代原图依据。出现分项矛盾或无法说明具体差别时，主agent先检查尺度/边界定义；只为未解决项补一次测量或有界复核，不默认等待用户纠错，也不靠更多代理投票定稿。
5. **有依据才换档，确认后固定。** 通常只比较当前值与一个有依据的相邻档位，不遍历所有尺寸或追SSIM总分。结论写清选择、原图依据、残余差异与把握；证据不足时保留有依据的现有值并标待核，不把“更舒服”写成“更准确”。用户已确认的页面选择记录到页面使用说明；不因其他组件的偏差反复重选，不升级为项目统一尺寸。复核材料可复用，只重验变化部分。

最小交付是在现有对比报告中附同倍率局部图和上述四项结论，并记录实际图标尺寸及来源。不要求为每个道具另写长文或新建测试系统；程序字段检查仍只证明执行正确，不能自动证明视觉选择正确。

### 组件放进容器：默认居中，偏移要有依据

适用于设计上居中的道具格、卡槽等：组件根节点默认以容器中心为锚点和轴心，位置为零；尺寸按已定义策略处理，内部图标与文字关系保持不变。不是把所有页面元素一律居中；明确要求靠边、顶对齐或由布局组件排列的内容遵循对应设计。

- 替换旧组件时，旧实例的位置不是正确答案。先检查父子关系、锚点、轴心及实际中心；顶部锚点下的位置零不是居中。不要无依据继承旧偏移，也不要为给文字留空间擅自上移整个组件。
- 复用原组件时，内部已有的正确几何关系可以由其他锚点/边距实现；不能只为让字段变成零而改写内部结构。默认中心零偏移约束的是新组件根与其目标容器，尺寸仍须单独查证，不能用居中通过代替尺寸验收。
- 默认居中后先看实际尺寸效果。透明边距、箭头顶饰和不对称轮廓是排查线索，不自动产生视觉补偿；小幅估算差异不足以新增偏移。确需例外时记录依据、适用范围和参数，优先用共用容器规则，不逐个道具修位置。
- 验收分两层：组件内部的图标/文字/样式；组件整体与容器的位置/尺寸/状态。内部Audit通过不代表页面通过；改动范围正确也不代表视觉位置正确。保存后检查真实实例相对父容器的中心偏差，再看代表状态实际截图。
- 独立插画上的覆盖物还需对照可见的定位标志，例如上下边缘、承托面或插槽：绝对屏幕坐标相同，不代表与底图的相对位置正确。父子层级一致也不能替代此检查。先分清底图位置/比例、覆盖物局部位置与整组适配各自的误差，只修有依据的一层；补偿值只记录在该页面，不形成通用固定偏移。
- 对应工具为 `UIDesignComponentRecipe` 的容器定位与检查入口：明确直接父容器，默认零偏移；有布局驱动时由原布局规则处理，不能静默争抢位置。机器检查验证声明被落实，不能证明声明本身符合美术设计。

### 当前工具范围（2026-11-09）

`scripts/compile_design_styles.py --binding ... --preview`与`UIDesignStyleRecipe.Apply/Audit`保留schema1的文字字段试验入口，不宣称完整组件合规。新的`--appearance <JSON> --output <packet>`及同一类的`ReadAppearance/ApplyAppearance/AuditAppearance`处理schema2完整外观绑定：图片的Sprite、Simple/Sliced、源border、颜色、材质和采样后的显示策略；文字的字体、材质、完整字重、自动字号、颜色、排版与明确的实际阴影组件。校验调用方显式登记的文件哈希，并要求直接资产及其meta有指纹；不会自动枚举shader、字体图集、全局阴影配置等间接依赖闭包，重要间接依赖需由调用方显式登记；未知字段、未消费参数和原节点布局字段拒绝，项目素材编号及参数只放项目映射。它仍不是任意组件或业务生成器。

完整组件复用仍须补齐上述实现关联和代表验证。本试验通过不能被后续代理误读成“所有规范已经可以自动执行”。

补充验证：`UIDesignComponentRecipe.cs`在文字工具上增加源组件子树复用、显式尺寸策略、项目阴影预设、保存后布局/样式核查。目前只验过普通方形图标＋数量，不支持任意组合组件；项目参数与源Prefab关联放项目实现描述里。页面填内容后必须调用其Audit，失败时不能交付。此普通物品组件的数量样式要求TrueShadow，不推广为所有图标或文字都要附加阴影。

别名不是完整样式：阴影预设可能只定义部分参数，仍需关联实例颜色/开关与实际加载的全局配置。生成后核对实际值，防止属性接口中的颜色转换改变原值。旧组件字段与美术规范有冲突时，明确哪项采用哪份依据；某材质字段有差异也不一定启用，不能据此断言一定有视觉差异。

文字溢出与外缘裁切分开：SDF字形网格包含描边留白，末尾字符推进距离还含侧边空白，均不能直接当字面宽度。结合字体实际字面范围、原引擎溢出模式和视觉检查。某些Overflow模式主动忽略横向超框，不能只信一个布尔标志。测试应包含可容纳的长文字、真的放不下的文字和恢复；不能不断放宽阈值让坏输入通过。

接入页面后反查实际嵌套实例，分开记录组件基准值和实例缩放后的有效值；模板通过不能代替页面通过。使用真实内容和活动状态：空串/停用TMP可能保留旧字符缓存，此时不测字面，但仍查显隐、布局、资源与样式；非空文字缺少字形数据则明确失败，不临时换成测试文案冒充该状态通过。保留旧页，在相同渲染环境做前后对照并核对改动范围，避免替换组件时顺手重建整个页面。

### 完整外观与仅改表现的修正

- 以保存后的实际Prefab及实例覆盖为起点，先锁定既有节点的父子、顺序、RectTransform和绑定，再应用获准的表现字段。schema2用`CaptureGeometry/AuditGeometry`检查既有节点不变；明确声明的附属文字层可追加，TrueShadow自动生成对象须按实际组件及owner识别，不能按名称宽泛豁免。临时预览对象不写用户全局Undo，新增对象先归属目标场景；常规场景编辑仍使用原生Undo，避免临时对象污染当前场景dirty标志。保存重载再独立对照布局；更换图片不等于可以照搬原页面尺寸。
- 按完整按钮和完整文字选型，先在当前框内比较少量整套候选，再应用全页。按钮底图、拉伸方式、源border、材质与颜色一起核对；文字的字体、材质、字重、自动字号、实际阴影或多层组合一起核对。多层文字先核实祖先显隐与原更新入口，静态附属层不冒称已接动态文字同步。
- 分开记录PNG烘焙底影、TMP描边/underlay和TrueShadow。材质存有参数不等于关键字启用；已有阴影不重复叠加，未声明阴影不自动添加。schema2显式选择`preserve/none/explicit`；源材质只读，需适配时使用局部副本。启用全局角度时查实际全局配置与最终Offset，不拿组件缓存角度当有效方向；新建或停用对象也要检查setter更新后的真实向量。
- 参数回查只证明字段已生效。必要时保持相同素材、尺寸、数据和渲染条件，做组件阴影开关或层开关对照，检查实际边缘、厚度、字面和输入命中。只批准表现修正时，布局锁失败就停止该改法，不靠移动对象补偿。微小残差按本轮目标停止，不扩大到未授权区域。

schema2目前支持原生Image/TMP、专用单Sprite、明确字段的TrueShadow，以及首次创建的静态文字附属层；不修改共享材质/Importer或全局阴影设置。烘焙阴影是来源声明，不是像素自动鉴定；baked TrueShadow及Plugin色溢模式明确拒绝。机器校验、实际引擎效果、独立复核和用户确认继续分别记录。

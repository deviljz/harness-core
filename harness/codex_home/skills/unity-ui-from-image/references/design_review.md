# 设计检查与交接

美术的核心入口是“准备交付”：美术认可图稿后，由AI检查缺口、准备元素并整理程序能接手的交付包，不要求改变创作工具或创作顺序。也可单独执行状态检查；只要求检查或清单时不自动切图、改图或组装Unity。提问与查证是手段，问题清单不是完整交付成果。

## 准备交付：美术的核心入口

用户说“这版可以交付了，帮我准备交付”等，即启动以下工作；仅表示图好看不等于要求执行交付。先按初始化规则查已有资料，缺项集中问。一次针对当前界面，不扫描或整理整个项目。

1. **检查并补齐状态。** 先查需求、原型和通用规范；按已确认规则补必要状态资料。需要决定玩法、交互含义或明显改变设计的，集中给负责人确认，继续不受影响的部分。补全清单不冒充已完成图稿。
2. **准备可用元素。** 有现成资源就引用并核对版本，有独立图层就检查并导出，只有整图或资源不完整时才调用流程1.1–1.5做必要的拆分、遮挡补全和验收。保留原稿，在交付目录工作；先分清界面归属，不重做预览背景。用组合效果核对明显残底、粘连、缺失和错位，不能因已有PSD就假定资源可用。缺少执行工具时明确受影响项，不把待做事项宣称为已导出。
3. **整理交付包供美术查看。** 必需内容是效果/必要状态图、可用资源或明确引用，以及简短交付清单（资源/字体/组件编号与版本、可变内容、状态说明、数据来源和缺项）。输出可读描述；已有机器描述则保留并核验，不强制为每张图另做完整精确标注或特定格式。汇总主要差异和仍需决定的事项，让美术确认本轮交付结果；不逐项增加审批。

**描述与标注按来源区分。** 已核实的设计文件或拼图数据直接保留，转换时不丢来源、单位和版本。图像测量与推断按字段标为“估计”，无法判断的标为“未知”；像素字高不等于TMP字号，不能从效果图猜出材质参数后当成已确认规范。详细布局标注按需要输出；缺少精确参数本身不阻塞交接，注明程序侧需要校准的部分。新补图、估计数据的确认与原稿认可分开，不默认已经获批。

程序接手后校验并复用已交付资源与可信描述，只处理缺口，不重复拆图。达到可用目标后记录低收益偏差，不无限精修。此入口不进入Unity，不替代业务/引擎验证，也不扩展后台监听或自动维护素材库。

## 美术与程序的边界

美术阶段可以完全不使用Unity。规范维护、效果图/状态补全、素材选择、布局标注与交接均可基于图片、图文规范、素材和样式目录完成；不把原Prefab、Unity运行结果或MCP连接作为美术开始工作的必需输入。已有项目可由程序预先导出组件与字体材质的示例图、稳定编号、允许参数和版本；新项目没有实现时先完成设计定义，记录实现待接入。

美术交付效果/状态图、素材及样式编号、可变内容和明确缺项；已有父子关系、坐标尺寸、缩放/适配意图等可靠数据一并保留，缺少的精确参数不强迫美术猜填。Prefab/GUID、TMP真实字形、阴影渲染、事件和业务接入属于程序阶段的映射与验证，不能要求美术为完成设计交接逐个查Unity组件字段。美术可以引用已导出的材质/组件编号，不代表本轮引擎实现已通过。

分开记录设计确认、文件/参数校验和引擎效果验证。没有Python时可继续设计、阅读图文目录并交付数据，标明机器校验尚未执行；程序接收后先做校验，再进入Unity。不要把“必须在Unity中验证”提前成美术阶段必须安装Unity，也不要因此省略程序阶段验证。工具依赖和交付方式见[执行环境](environment.md)。

## 提问和调查的范围

只追问会改变“画什么、如何变化、如何布局、哪里可操作”的信息。触发条件描述到UI能区分状态即可；产生状态的完整业务算法不是美术交付的前置条件。例如特殊标记的出现算法未知，但已明确有/无两种表现、依附对象和点击行为，就可以设计两态并注明触发由业务提供。不能因此编造算法，也不能因算法未知把整页美术卡住。

若未知信息会改变可见状态种类、对象关系或整页结构，仍须查证、请人决策或明确延期受影响部分。点击后去哪可引用已有页面；没有目的页时先标明待接入，不擅自设计玩家资料、商店等新功能。

## 一轮怎么执行

1. **定范围与材料。** 明确本次界面、入口及必要关联页面，登记效果图、策划案、原型及其版本/日期。若本次任务是验证或完善流程，案例只用于验证方法，不自动转为界面改造任务。
2. **列视觉缺口。** 根据实际界面列出缺失状态、布局联动和交互标注；先识别共用规则，不为相似按钮重复分析。仅把影响美术设计的未知点变成调查问题，不立即发一整份业务问卷。
3. **找答案并做有界验证。** 只有图就整理需要人回答的问题；有材料就先查已有说明，再用最少的代表状态验证会改变交互含义、素材范围或流程的关键疑问。采用下面的查证与检查方法。
4. **输出美术补全清单。** 把答案转换为具体任务：在哪个区域补什么、保留/隐藏/替换什么、布局与点击关系、文案草案、交付形式及验收条件。区分已确认要求和AI建议；共用状态只设计一次。不用“补空态”等模糊待办代替设计任务。
5. **美术补全与确认。** 根据授权由美术或AI补必要状态图及标注；用户只要求清单时停在清单。优先局部状态板和文字约定，结构变化才补整页。只提交仍影响设计的歧义、建议和范围决定，不重复问已确认内容。
6. **核对后交接。** 按补全清单验收实际图稿/说明与覆盖范围，形成程序交接资料，记录明确延期项。补全清单已写好不等于美术已完成。若本次请求是“准备交付”，继续执行上面的元素准备与交付整理；若只要求状态检查，则停在该范围。两者都不自动进入Unity。

## 用户授权不提问时

“不提问”不等于跳过状态设计。把可见事实、采用的试作假设、仍未知的真实规则分开；选择可替换、无真实交易/存档副作用的表现完成本轮。交付补全清单、实际状态图和假设清单，不冒称设计已获业务确认。未知触发条件保留为外部输入，不因做了状态预览就补造完整玩法。

原图截断的列表项只能证明存在部分外观。先区分被遮挡的美术与根本未提供的商品/奖励/文案；后者采用明确标识的无操作占位或记录延期，不凭同类项复制出真实内容。可见部分仍应保持正确布局和滚动关系。

## 两个执行时机

- 出图前：结合需求、流程和已有设计规范，建立控件与状态约定，交给美术或AI出图。
- 出图后：对照约定查漏。只有现成图时，先登记图中事实，再提出推测和问题；不能从单张效果图反推出完整业务规则。

## 检查方法

### 先按已有材料找答案

- 只有效果图：记录可见事实，把业务条件与不明确交互交给人回答；AI建议明确标为草案。
- 有策划案或可操作原型：先把问题对应到材料位置、页面入口与测试条件，AI在已有授权内查证，再汇总给人确认。不要把资料中已有的答案重复抛给用户。
- 每条结论标明依据是文档描述、原型提示、实际操作结果、视觉观察还是推断，并记录来源、日期、复现路径与前提。文案说明过的规则不等于边界已实测；原型实现不等于负责人已批准的最终设计。
- 文字事实优先留短摘录和定位；只有判断外观确有需要才看图。必要截图留本地并关联状态，不反复把整图送入上下文。工具超时只代表本次调用失败；重试前先核对当前页面，避免重复执行已生效的动作。工具连接故障记为验证限制，不记成产品没有该状态。
- 材料与图、文案与行为冲突时，列出冲突和影响，不静默选一个当真。测试场景的名称不代表完整条件，切换后核对实际资源、进度和显示状态。
- 优先用明确的测试场景验证关键分支与边界。替换持久化试玩数据要先确认授权，结束后记录停留场景；“切回默认”不等于还原原存档。没有便捷入口时列出未验证项与最小补测方法，不为耗空资源或达到高进度无限操作，也不把没观察到当成不支持。
- 检查范围以本次界面及理解其状态所需的直接弹窗/关联入口为限。关联页面另列任务，不无意扩展为整个产品验收。资料足以回答的问题填入状态表；最后只问剩余歧义、冲突、范围和需要批准的决定。

### 逐项检查

1. 先找操作入口、状态展示、资源、选择关系和内容容器。记录观察证据；“形似按钮”“看起来像选中”只是推断。
2. 沿界面线索检查相关状态。锁标记提示锁定/解锁；输入与确认提示有效/无效；价格与资源提示足够/不足；列表或网格提示有内容/无内容；明确存在异步获取时才考虑加载/失败。无关项注明不适用，不套全状态清单。
3. 对每个相关状态分别填写触发条件、视觉表现、点击/输入行为和离开该状态的条件。不能执行操作不等于不能点击，可能仍需解释原因或引导。数值不足不自动等于按钮置灰；空内容不等于加载中。
4. 分清事实、设计建议、待确认项和已确认决定。业务条件由需求负责人确认，美术表现由约定的设计负责人确认；AI可推荐，不凭空确定扣费、解锁、跳转或优先级。
5. 先问共用规则，再问例外。优先问会改变交互对象、素材种类或状态结构的问题；低影响表现可提供草案，明确未经确认。不要逐个按钮重复提问。
6. 检查真实可能发生的状态组合，例如锁定且资源不足；确定哪种提示优先，以及是否需要同时展示。只覆盖有依据的组合，不枚举所有排列。
   模式切换检查联动区域与返回后状态；红点等提示明确有/无表现及依附对象，触发/消失规则仅追到影响UI设计的程度。数据为0时先确认容器展示“已拥有内容”还是“完整目录”，不能一律要求空白页。DOM角色或一次点击无响应只能辅助判断，不能单独证明元素永远没有交互。
7. 调查结论必须落到美术任务或“不需补图”的明确说明。每个状态可以通过文案/颜色/显隐约定、局部状态图或额外整页表达，不要求每个状态重新画完整页面。

## 输出及完成条件

使用[状态约定模板](../assets/templates/state_inventory.json)。已有设计系统可被引用，不重复维护同一规则。

### 输出一：给美术的补全清单

每项包含：对应区域与状态、已有参考、保留/隐藏/改变的内容、布局及交互要求、文案（区分定稿/草案）、交付形式（标注/局部/整页）、可观察的验收条件、已确认依据及待定项。共用要求集中写，案例数量与具体数值不做通用模板默认值。

如列表为空，必须说清保留哪些页头/标签/固定栏、清空哪个容器、提示位置与文字、是否有操作入口。不要只列状态名，也不要未经授权添加加入队伍、领奖或购买按钮。

### 输出二：给程序的UI状态设计包

美术补全后汇总，不强制特定文件数量或格式：

- 页面及必要状态图：每张图标出代表的状态、版本和来源。
- 状态变化说明：显隐、换字、颜色/徽章/进度变化及共用样式；精确业务计算可由外部数据提供。
- 布局联动说明：固定区、滚动区、分组、遮挡及切换时保留/替换的区域。
- 交互标注：可点对象、点击范围、反馈与关联页面/弹窗引用；只标事件入口时说明目的页未纳入范围。
- 覆盖与延期清单：每项能定位到实际图稿或明确规则，剩余缺口及影响写清。依据、设计批准与实际验证分别保留。

以上是交付包中的状态设计部分，不等于已完成资源准备。“准备交付”还要核对或补齐可用元素；单独状态检查则不切图。交互和布局说明可用简短文字，不强制另画详细参数标注图，也不要求确定Unity节点或脚本。

### 完成判断

- 调查完成：已发现相关缺口并收集答案/列明未知；不等于已有可执行美术任务。
- 补全清单可执行：美术能明确按项补图；不影响表现的业务算法可以延期。仍有视觉选择时标出建议稿，不能冒充已确认要求。
- 程序可接手：必要图稿与说明已交付并核对，程序无需再猜缺失状态长什么样、哪些一起变化、哪里能点。不能仅凭问题已回答、文件存在或隐藏节点测试称通过。

分别记录清单准备、设计确认、美术覆盖、程序交接状态。用户只要求清单时交付第一份输出，第二份输出标为待美术完成；不得把任务列表本身包装成已完成的状态设计包。已确认部分可供后续使用，但不宣称整页状态已覆盖。

## 与后续阶段的边界

设计检查与交接提供有版本的设计依据；阶段1.1根据依据定义独立素材与复用，1.2处理素材内容的遮挡/完整性，阶段2实现已确定表现和交互绑定。后续发现新状态，回到设计检查与交接对应控件补定义，再更新受影响部分，不全流程推倒重来。

后续发现问题时，先定位：状态/操作含义未定义属于设计检查与交接，独立对象定义不当属于1.1，素材不完整属于1.2或后续制作，实现没有遵守已确认约定才属于组装问题。保留原决定与新证据，标明最早出错位置和影响范围，不把后来的局部修正冒充通用规则。案例中的具体胜场、资源名和解锁数值只留案例，不写成通用默认值。

此阶段也执行边际收益原则：优先消除影响操作含义和素材范围的歧义；不为本次无需支持的极端场景扩张设计。必要的状态定义不是可随意跳过的美术精修。

## 动态表现也是美术交接内容

从图中发现的星光、放射光、拖尾、流光等先分类为静态材质、独立特效或待确认。单帧不足以确定是否循环、何时触发；有视频/可操作原型先查证，只有图时按授权提问或标明试作假设。

补全清单要说明跟随对象、前后层级、透明混合、基本时间表现、开/停/恢复条件和是否影响点击；必要时交局部动态示意，不用静态合成图代替动态设计。素材包包含不带效果的干净主体与可独立控制的效果；普通表面高光不自动拆成特效。不从一张奖励图擅自补造飞币、领取庆典或完整购买流程。


### 界面归属与正式交付检查

设计前按“本界面自有／共享复用／仅宿主预览／未知”声明可见对象和依据；未知先查资料。压暗不能单独决定归属，自己的遮罩和disabled状态仍可能自有。只验自有范围及本页采用的共享组件，不重做宿主画面。正式导出再执行一次归属检查：不含宿主图、重复宿主UI或有渲染的占位；挂接点应无渲染和输入。仅将previewData设null不够，还要用空数据清除已保存动态值并验证恢复。示例数据与宿主组合放Preview层，保留自身遮罩/输入拦截，开关与页面一起生效。

# 美术与程序分别需要什么环境

Skill是流程说明和工具索引，不是运行环境。下表区分当前可执行能力与准备建议；项目版本、路径和许可证来自本项目，不复制其他案例的绝对路径。

| 工作 | 美术是否需要Unity | 当前工具依赖 | 无工具时怎么办 |
|---|---|---|---|
| 需求/状态检查、规范与效果图评审 | 不需要 | 能看图和文件的AI/人工工具 | 仍可完成设计与问题清单 |
| 使用素材、字体材质、组件图文目录选型 | 不需要 | 浏览器/图片查看器、已导出的目录 | 资料不足标缺项，不要求美术去反查Prefab |
| 编写布局标注、素材清单和设计交接数据 | 不需要 | 文本/JSON或团队已有标注工具 | 可先交设计，声明机器校验待执行 |
| 准备交付中的资源导出、必要拆分/补全及组合核对 | 不需要 | 已有资源/设计文件、图像处理脚本；复杂补全需可用图像工具 | 复用已可用部分，明确缺工具导致的未完成项，不将清单冒充实际资源 |
| 程序接收后的组件声明校验（可离线） | 不需要运行Unity | Python 3标准库、目标项目资源文件和组件配置；compile_component_declarations.py | 放在程序侧执行；美术只有图文目录时不能执行依赖Prefab文件的这一检查 |
| 生成当前规范库HTML | 不需要 | Python + PyYAML；build_design_library.py | 使用预先生成的HTML；不要求阅读者安装Python |
| 图像测量/局部对比/复核包 | 不需要引擎；若比较实际UI需程序提供截图 | 按工具使用Pillow/numpy/OpenCV等；当前ui_review_gate也间接依赖pipeline_common图像库 | 将此执行放在配置好的工作机，交付可直接查看的报告 |
| 素材/样式映射到Prefab、生成和保存 | 需要 | 项目匹配的Unity Editor、uGUI/TMP、该项目实际组件/插件与Editor工具 | 程序阶段先补环境与映射，不用截图拼贴冒充可编辑UI |
| 引擎渲染、适配、状态和输入验证 | 需要 | 项目渲染管线与字体/材质等真实依赖 | 未运行的范围明确待验 |

MCP只负责AI与已打开的Unity编辑器通信，不负责渲染本身，不是美术流程必需条件。当前本机控制链是Python/uv启动MCP客户端→Unity MCP包→Editor C#工具；其他环境可以改用团队已有菜单/批处理/编辑器接口，但必须实际提供并验证入口，不能仅凭理论可替换就声称已经支持。共享工程运行时优先使用已有可见编辑器，不另起隐藏实例。

## 给美术的最小交付

先提供可直接打开的HTML规范库、示例图、素材目录与设计交接格式。组件/材质以稳定编号引用，页面坐标属于设计画布；Unity路径、GUID和代码入口由程序维护的映射解决。已验证的Unity实现可预先导出示例，后续资源或组件变更按版本增量更新目录，避免每位美术重复扫描整个工程。

美术需要AI自动运行校验时，由团队准备一次运行器：可以是配好Python依赖的工作机，或以后打包的桌面/服务入口。当前交付仍是脚本与Unity工具，尚没有免安装桌面程序，也没有已部署的远程服务。不要要求美术自行敲命令，也不要声称只装skill就能执行全部步骤；将部署作为单独的准备工作。

## 接收任务时的环境核对

只核对本次阶段实际需要的能力。纯设计任务不检查Unity/MCP，不因未连接而阻塞；程序任务核对项目路径、编辑器版本、包/字体/阴影/渲染依赖、组件与工具版本、输出范围以及已有未保存内容。包安装与缺许可证分别报告，不把缺环境归为模型不够强。

交接先冻结设计数据和来源版本，再交程序解析与机器校验。引擎发现布局/字体/组件不支持时，指出属于设计缺项、映射错误还是实现限制，只退回受影响部分，不静默修改设计规范求通过。

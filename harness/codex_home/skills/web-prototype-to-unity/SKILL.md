# 网页版还原到 Unity

先固定正式网页的提交或构建号和 Unity 检出版本。同步任务先读交接，再沿网页实际入口操作。文档与网页表现有冲突时核对两个版本及用户明确要求。有高影响的玩法歧义就记录，继续确认得了的部分。用户已指定的共用组件、居中和适配约定优先。

## 一轮怎么做

1. 先独立列受影响的真实入口、可见状态和动态触发。每个状态记录同一存档或种子、视口、安全区、入口动作。复用现有验证脚本和主工程代码，遵守用户指定的工程路径。单独测 UI 时可以固定逻辑时间；流程回归保留实际时钟。
2. 静态从实际 DOM 盒子、computed style、实际字体以及真实加载的图取证。Canvas 画面从运行结果和实际绘制代码定位。复用确认为正确的网页原资源，核对哈希或像素、裁切、透明边和取图姿势。记录 Unity 导入后的尺寸、压缩、字重、描边、阴影及渐变，避免按整体截图猜数值。
3. 把动效当作单独的验收项。用同一业务事件作时间零点，两端走真实触发；记录出现前、关键动作、中段、消失或落定。常见一次性效应用按时间排列的多帧或视频，循环效应至少看过一个周期。记录实际采样时间和可见状态，关键时刻需要比较就补拍。动态证据和常见漏项见 [动态验收与回归](references/motion-checks.md)。
4. 对差异按证据做最小修改。沿用原玩法、真实业务入口和已有组件资源。表现用连续时钟，按真实锚点跟随正确层，规则只提供触发和数据。时间与视觉参数取自实测、关键帧或网页绘制代码。
5. 用同样的入口复测，覆盖确认、取消、再开、重复触发、短屏和相关视口。做截图或视频报告时，每个动态用例给触发和时轴、点图或播放入口、未验证项。保留关键可复现材料。只要求核查时留问题和证据；已要求修复就实施并复测。

## 每轮维护

结束前检查此次是否发现会重复发生、且现有步骤抓不住的问题。将证据整理为「问题、怎么复现、提前怎么查、通过的条件」，去重后写进参考。特定项目的版本、坐标、时长和取舍留项目记录，不当通用默认值。已有规则没执行时补对应检查或脚本，避免再堆一句提醒。有旧结论被推翻就更新原条目与报告。无新增教训只更新本轮运行记录。

需要从网页持续生成可编辑 uGUI 时，复用浏览器排版后的节点数据来生成 Prefab，并将交互、动态数据和动效接回既有 C#。Camp 的具体生成、重跑与验收流程见 [Camp 网页取样与 Prefab](references/camp.md)。

# Windows 性能排查

先取得卡顿时的本机证据，再决定最小处理。当前用户限制优先；调查请求本身不授权结束进程、关闭应用、切换忙碌对话面板、删除 Git 锁或更改仓库。已有授权不重复询问。

## 一轮轻量采样

复用 [scripts/sample_cpu.py](scripts/sample_cpu.py)，不要另写同类进程轮询脚本。它源自本机已有采样器，使用 Windows 原生计数，不依赖任务管理器刷新或 WMI 性能类。

先定位现有 Python；找不到时可用 load_workspace_dependencies，不为采样安装一套环境。传递脚本的实际路径：

```text
<python> <skill-directory>/scripts/sample_cpu.py --seconds 20
```

默认约 20 秒、单轮最多 60 秒；输出报告路径与概要，报告写入系统临时目录而非工作仓库。只有新证据或对照确有需要时才追加采样，不以反复扫描代替定位。不创建定时任务；持续监控仅在用户另有要求时配置。

报告包括整机/进程 CPU、线程数、Git 父进程来源、工作目录及操作类别。只在本地短暂读取 Git 自身参数，提取白名单字段；不保存完整命令行，不读取聊天、源码或账号数据。

按需要补充：

- 内存：读取 Win32_OperatingSystem 可用物理内存，结合系统提交量/上限及换页判断，不只看最大工作集。
- 磁盘：有界读取延迟、队列和吞吐，不能只根据吞吐判断堵塞。WMI 性能类为空表示未取得数据，可改用 PDH 英文计数器；不要因此重置计数器或重启服务。
- 采样时负载已降低，说明窗口可能不同。保存本轮证据，再找当时日志或下一次发作时采样。使用远程控制不等于网络就是原因。

## 归因边界

- 当前高 CPU 不自动证明之前的长时间满载都由它引起。进程名称不等于用途，核对可执行文件及父进程。
- CPU 百分比按整机逻辑处理器总量计算。短命进程可能被漏采，系统与进程计时略有错位；各进程不必在单个采样里恰好加到 100%。
- Git 分清桌面后台、agent/终端命令、其他编辑器，再按仓库比较。失败日志可能不记录成功操作；取消条数不等于所有调用次数，也不自动等于死循环或超时。
- 原始文件通知不等于实际重扫；忽略文件重建也可能产生父目录通知，需要验证后续过滤行为。锁文件的年龄或一次可独占打开，不足以证明可删除。

## 最小可逆处理

围绕关键假设做有界对照，复用已有配置、监视器和工具。额外的 Git 检查可能加重卡顿；需要时只运行一次有界对照，使用 --no-optional-locks，隐藏文件列表与正文，记录测试范围和后台负载。

Git 扫描线程过多时，可测试命令级临时参数 -c core.preloadIndex=false -c index.threads=1。可能降低 CPU，也可能增加等待；不能作为固定优化。比较 CPU 时间、实际耗时、输出是否一致后，按授权决定是否写对应仓库配置。

更改时保存精确原键值和本地备份，明确作用仓库，保留 fsmonitor 等无关设置。恢复只还原本轮键，不整份覆盖其他任务可能刚改过的配置。不禁用 Git 代替解决扫描问题，提交、更新功能必须保留。

报告时间窗口、主因证据、改动、效果与代价、未验证项和恢复方式。未经实测生效不能说已修好。
